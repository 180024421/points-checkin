## 1. 业务背景（Business Context）

### 1.1 它解决什么问题
WorkBuddy 与 TraeWork 这类 AI 编码工具以「每日签到 + 成长中心任务」发放积分，积分直接影响可用额度与功能。收益要拿满，用户必须：

- 每天在**早、晚两个时间窗口**分别签到；
- 对**多个账号**重复签到，WorkBuddy 号还要顺带跑成长中心任务；
- 时刻盯着 token 是否过期、活动入口是否开放、积分是否到账。

手动做既费时又极易漏签，漏一天连签就断、积分就少一截。CheckinTool 把这件事自动化：一次配置，之后到点自动跑，跑没跑成在看板上一目了然。

### 1.2 为什么现在做 / 商业动机
- 目标人群（重度多号 AI 工具用户、羊毛/额度党）在扩大，「多号 + 双窗口 + 签到 + 成长任务」的手动成本随号数线性上升，自动化价值随之放大。
- 采用**卡密授权**分发：工具是获客载体，卡密（按时长 / 按可挂载账号数）是变现方式；服务端代跑与代做成长任务是可持续收费的增值能力。
- 🔶 假设（待确认）：首年目标 GMV / 卡密销量 / 付费转化率、代跑服务器月度成本上限、目标上线时间。建议草案见 §12。

### 1.3 产品边界
覆盖：本机签到调度、成长中心任务、多账号入池、授权服务端代跑、今日看板 / 积分记录 / 日志、通知、卡密门禁与额度、备份恢复、桌面端界面体验。
不覆盖（另立规格）：卡密管理端、发卡与计费后台、服务端代跑调度算法本身。

## 2. 干系人与用户（Stakeholders & Users）

### 2.1 干系人
| 角色 | 关心什么 |
|---|---|
| 终端用户（付费买家） | 签得上、任务做得完、不掉线、看得懂今天跑没跑、别把我账号弄丢 |
| 产品 / 运营 | 卡密续费率、代跑增值转化、客服工单量（登录失败、token 过期） |
| 授权与代跑服务运营方 | 额度发放、吊销、服务端负载与凭证保鲜成本 |
| 开发 / 架构 | 需求稳定、验收标准可测 |

### 2.2 目标用户画像
**Persona A —「多号额度党」老周**
- 持有 5～15 个 WorkBuddy / TraeWork 账号，为攒积分 / 保额度。
- 痛点：手动逐个切号签到 + 做成长任务耗时；早晚两窗记不住；换号后 token 失效不知情。
- 诉求：一次入池后完全无人值守；漏跑能自动补；哪个号坏了要能一眼看到并收到通知。
- 技术水平：中等，能照说明操作，不想读报错术语。

**Persona B —「尝鲜单号用户」小敏**
- 只有 1～2 个号，怕麻烦、怕被封号。
- 痛点：不确定「自动签到会不会违规 / 丢账号」；被验证码 / 扫码挡住就放弃。
- 诉求：最低成本把每日签到 + 成长任务外包掉；出问题希望有邮件通知。

### 2.3 非目标用户
企业批量矩阵号运营、需要 API 化 / 大规模并发签到的团队——现有产品形态（桌面 EXE + 卡密）不为其设计。

## 4. 用例（Use Cases）— 核心，权重最高

### 4.0 需求优先级总览（MoSCoW）
| 用例 | 优先级 | 说明 |
|---|---|---|
| UC-1 卡密激活 | Must | 门禁，无它不可用 |
| UC-2 多账号入池 | Must | 核心价值入口 |
| UC-3 每日自动签到 | Must | 主用途 |
| UC-4 服务端代跑 | Should | 增值 / 变现主渠道 |
| UC-5 成长中心任务 | Should | WorkBuddy 完整收益必需 |
| UC-6 查看今日结果与积分 | Must | 用户信任来源 |
| UC-7 通知（站内 + 邮件） | Should | 无人值守下的兜底 |
| UC-8 单账号 / 刷积分即时执行 | Could | 精细控制 |
| UC-9 备份与恢复（同机） | Should | 换机迁移不承诺（凭证绑机器） |
| UC-10 状态自动同步 | Must | 免手点 |
| UC-11 停用/启用 · 清理 · 换主题 | Could | 日常运维 |

### UC-1 卡密激活并进入使用 〔Must〕
1. 用户首次启动 → 输入卡密（`points-checkin`）→ 绑定本机设备 → 进入主界面，顶部显示「可挂载账号数」额度。
2. **异常**：卡密到期 / 被吊销 → 踢回激活页并清票据；重输有效卡密即恢复，无需重启。
3. **异常**：断网 / 加密通道建不起来 → 只累计失败次数，**不踢人**（避免误伤离线用户）。

### UC-2 多账号入池（本机）〔Must〕
1. 在已登录的官方客户端切到号 A → 点「采集」；退出登录号 B → 再采集；列表出现多行。
2. 可按号分别设「本机跑 / 服务器代跑」。
3. **扩展**：TraeWork 无法自动解密 token 时改用「粘贴 Trae token」，设备头自动带上。
4. **异常**：统一登录遇扫码 / 强验证码 → 引导回「采集 / 粘贴 token」。

### UC-2b 统一登录导入账密〔Must 的备选入池方式〕
1. 「导入账密」填产品 + 邮箱/手机 + 密码（支持批量每行 `provider,username,password[,label]`），可勾选立即登录。
2. 成功自动写入账号列表，可直接本机签 / 代跑。
3. **异常**：WorkBuddy / Trae 多为 OneID/OAuth，纯密码常不可用 → 自动开浏览器；遇扫码 / 强验证码改回采集 / 粘贴 token。账密仅本机加密存储。

### UC-3 每日自动签到（本机调度）〔Must〕
1. 到早窗（默认约 09:10）自动跑一轮，晚窗（默认 20:00 之后）补跑未成的。
2. 一个账号出错只影响它自己，后续账号与另一窗口照跑（不再整天静默停摆）。
3. 账号间走**可配错峰随机间隔**，避免同刻并发用同一 token 打供应商。
4. **异常**：活动未开始 / 入口未开放 = 第三态「未开放」，既不算领到也不算失败，晚窗仍可补。

### UC-4 授权服务端代跑〔Should〕
1. 选中账号「设为服务器代跑 / 上传代跑」。
2. **前置**：必须先绑定并验证联系邮箱（异常时服务端发邮件通知）。
3. 上传的是 **token 而非明文账密**；额度以服务端「代挂额度」为准，换卡密后立即重拉。
4. 可顺带让服务器代做 WorkBuddy 成长任务。
5. 本机定期做**凭证保鲜**：把刷新后的 token 回传服务端（服务端不会自己续期）。
6. **异常**：额度已满 → 拦截入库并提示；服务端不可达 → 不因「查不到状态」误拦，最终由服务端裁决。

### UC-5 成长中心任务（WorkBuddy）〔Should〕
1. 本机签到后顺带对该 WorkBuddy 号跑当日成长中心任务（含聊天类任务，可开关）。
2. **幂等**：已完成 / 已领奖自动跳过，同一天不重复跑。
3. 三态模式：off（不做）/ local（本机做）/ server（服务器代做）。
4. **异常**：非 WorkBuddy 账号 → 提示「无成长任务」跳过。

### UC-6 查看今日结果与积分〔Must〕
1. 「今日看板」看已跑 / 未领（未开放）/ 待办 / 异常四档。
2. 「积分记录」看每次签到拿到的积分与连签天数；积分无变化不写记录（防刷屏）。
3. 「跑批趋势」看近 N 天每日已签 / 失败 / 未开放 / 成功率，并列出期间反复失败的账号（回答「这周签得怎么样、哪个号老坏」）。
4. 「导出 CSV」把积分记录 / 跑批记录导出到数据目录 `export/`，Excel 直接打开。
5. 「实时日志」看过程，可清理；跨天记录带日期不串。

### UC-7 通知（站内弹窗 + 邮件）〔Should〕
1. 账号签到异常时站内**必发**未读通知（含运营公告），前端弹窗提醒、可标已读。
2. 绑定并验证邮箱后，同类异常额外发邮件（不绑定也能代跑，只是少了邮件这一路）。
3. 积分低于阈值（默认 100，可配）、token 将过期时在界面标 warn 提醒处理。
4. tkinter 回退端：账号新出现「签到失败 / token 过期 / 积分不足」时弹 **Windows 原生托盘气泡**主动提醒（同问题恢复前不重复弹）。
> PyWebView 主端仍以站内弹窗 + 邮件为主，托盘气泡是回退端补的兜底。

### UC-8 单账号 / 刷积分即时执行〔Could〕
1. 对单个账号点「立即签到」或按需刷积分，不等定时窗口。
2. 与整批签到 / 成长任务 / 凭证保鲜 / 自动同步共用**同一条串行通道**：同一时刻只有一份在问供应商，撞上提示「已有任务在执行」而非并发用同一 token。

### UC-9 备份与恢复（同机）〔Should〕
1. 「设置 → 数据管理」打包账号 / 日志 / 积分记录 / 配置为带时间戳的 zip；同机重装或误删后「恢复数据」选回。
2. 安全：只接受白名单文件，单文件 >20MB 拒绝（防构造压缩包越界）。
3. 轮转：本机备份目录只保留最近 N 份（默认 10，可配），超出自动删最旧，不再无限堆积。
4. **换机不在承诺范围内**：凭证与「当前用户 + 机器」绑定（DPAPI），换到新机器解不开、备份里也不含票据与设备身份——这是**刻意的设计**（防止备份被搬到别人机器直接续用），产品**不承诺跨机迁移**。
5. **异常**：换机后设备指纹变化，卡密若限设备数需管理端先清旧设备。

### UC-10 生命周期内状态自动同步〔Must〕
1. 启动约 4 秒后自动同步一次，之后按间隔（默认 5 分）刷新本机账号积分与「谁跑了」（含代跑结果走服务端聚合，界面每 30 秒重读，几乎不打网络）。
2. 同步主动让路：有签到 / 上传在跑时不插队；未激活时不打供应商接口。
3. 激活卡密成功或刚打开开关，立刻补一次同步，不等满间隔。

### UC-11 日常运维（停用/启用 · 清理 · 主题）〔Could〕
1. 停用账号不占额度、也不会在额度已满时拦住入库；额度只算「启用中」账号。
2. 可清理实时日志 / 跑批日志。
3. 界面主题三选：跟随系统 / 浅色 / 深色（体验需求，见 §6）。

## 6. 用户体验需求（UX Requirements）— 业务视角

> 具体视觉令牌 / 组件规范见 `docs/UI-设计方案.md`，此处只列业务层面的体验要求。

- **首要回答「今天到底签了没、还有什么是坏的」**：概览首屏优先呈现四档统计与「需要你处理」项，异常为 0 时收敛成一行绿字。
- **状态可读、不只靠颜色**：已跑 / 未领 / 待办 / 异常 / 停用要有文字与图标，色盲可用；「未开放」是独立一档，不能被误读成「坏了」。
- **反馈不刷屏、不误伤**：让路 / 已有任务在跑这类提示用非模态 snackbar，不弹阻断式对话框。
- **离线桌面优先**：常驻离线运行，不依赖网页字体 / 外部图标请求；窗口最小 980×640，窄窗靠收纳不靠缩字。
- **明暗双主题**：晚窗固定 20:00 之后补跑，需深色主题避免全屏白光；正文对比度须达可读标准。
- **术语友好**：报错与日志脱敏且用人话，普通用户能看懂下一步做什么。
- **备份含敏感凭证**：界面须明示「这是密码级数据，勿外发」。

## 7. 非功能与可靠性需求（业务层面）— 补

> 只写「业务能接受的程度的表现」，不写实现手段。

| 维度 | 业务要求 |
|---|---|
| 无人值守容错 | 单账号 / 单窗口失败不扩散；一个号抛错不得把整天自动签到静默停掉 |
| 重试与超时 | 网络失败与特定供应商错误码要退避重试，且每次调用有**总时长预算**兜底（草案：Trae ≈3 分钟、WorkBuddy ≈1.5 分钟），超时按失败记录，不拖死排队账号。口径是**单次 `retry_call` 级**；一个账号跨多个接口各自撞满时，累计时间可超过该数字（非整账号累计硬上限） |
| 幂等 | 同一天重复触发的签到 / 成长任务不得重复领奖或制造脏记录 |
| 并发安全 | 任一时刻只有一份请求在问同一 token（串行通道），避免并发触发风控 |
| 错峰 | 多号之间随机错峰间隔（可配），不得所有号同秒连打供应商 |
| 数据一致 | 界面重读只在数据真变时重建列表，不打断滚动 / 选中；日志缓冲落盘，强杀最多丢最近 2 秒 |
| 状态第三态 | 「未开放」既不标成功也不进失败统计，不得被误写成「已签到」而漏补跑 |
| 可用性 | 断网时已激活用户不被误踢；离线可继续用缓存额度 |
| 安全（凭证） | 账密 / token / 票据默认按当前用户加密落盘；明文降级须留警告文件 + 启动告警 |
| 安全（传输） | 与授权 / 代跑服务默认走加密信封；明文回退须默认关闭且仅应急临时开 |
| 交付 | 对外唯一形态 Windows EXE（无控制台），支持托盘常驻 + 开机自启 |

## 8. 业务约束（Business Constraints）— 核心，权重最高

### 8.1 合规与平台风险
- 依赖 WorkBuddy / TraeWork 第三方平台的签到 / 任务行为，存在**违反平台 ToS / 封号风险**；产品须向用户明示风险，不做隐蔽绕过。
- 涉及**个人信息**（联系邮箱、手机号 / 邮箱账号）：收集与用途须符合个人信息保护要求，最小化收集，仅用于异常通知；对外传输与存储须加密。

### 8.2 授权与商业模式约束
- 卡密门禁：设备绑定、按时长与「可挂载账号数」计额度；额度以服务端权威值为准（注意 `quota` 与 `accountLimit` 语义不同，见 §10）。
- 代跑增值：上传代跑前强制绑定验证邮箱；服务端为额度与绑定的最终裁决方。

### 8.3 交付与运行约束
- 依赖第三方运行环境（浏览器自动化组件），首次使用统一登录需在装机环境预置。
- 备用桌面回退端体验须与主界面同色系（不做同等视觉），不引入外部字体 / 图标请求。

### 8.4 功能实现状态（相对上一版 backlog）
- **换机迁移**：不再承诺（见 UC-9 第 4 点）——凭证绑「当前用户 + 机器」是防搬机续用的刻意设计，不算缺陷。备份范围收敛为**同机重装 / 误删还原**。
- ✅ 备份轮转：本机备份目录按 `backup_keep_count`（默认 10）保留最近 N 份，超出删最旧。
- ✅ 跨天跑批历史 / 趋势：近 N 天每日「已签 / 失败 / 未开放 / 成功率」+ 反复失败的账号榜（「签到记录」页）。
- ✅ 记录导出 CSV：积分记录、跑批记录一键导出（UTF-8 BOM，Excel 直接打开），落在数据目录 `export/`。

- 剩余候选（未排期）：趋势图折线可视化、跑批历史按周 / 月汇总。

## 9. 假设与依赖（Assumptions & Dependencies）— 补

### 9.1 外部依赖
| 依赖 | 说明 | 失效影响 |
|---|---|---|
| WorkBuddy / TraeWork 平台接口与签到 / 任务规则 | 收益来源本身 | 规则 / 接口变更即需适配，可能整体失效 |
| run-jane 授权 + 代跑服务端 | 卡密校验、额度、代跑、聚合看板、通知 | 不可达时本机仍可跑；代跑与额度校正受阻 |
| 加密通道 / 授权服务器 TLS | 传输安全 | 服务端未配 TLS，明文 HTTP 属临时状态 |
| 浏览器自动化运行环境 | 统一登录过验证码 | 未装机时统一登录不可用，退回采集 / 粘贴 |
| 邮件通知通道 | 异常邮件兜底 | 未绑邮箱 / 通道故障时只剩站内通知 |

### 9.2 关键假设
- 服务端契约字段（`quota`、`accountLimit`、`entitlement/info` 等）以**线上实测**为准，仓库快照不等于线上版本；解析需对字段名容错。
- 用户为「个人多号」规模（个位数到十几个号），非企业级并发。
- 平台签到为周期性活动，短期不会因反自动化彻底封堵（若封堵需重估产品可行性）。

## 10. 术语表（Glossary）— 补

| 术语 | 含义 | 易错点 |
|---|---|---|
| 卡密 / ticket | 授权凭证；激活后本机缓存 ticket，后台在线校验 | 断网不吊销，仅服务端明确拒绝才踢 |
| **quota（代挂额度）** | 「可挂载账号数」的**权威来源**，管理端按卡密 / 卡种配置 | 顶部额度标签显示的就是它 |
| **accountLimit** | 授权状态里的**设备座位数**，不是账号额度 | 离线时暂退回它，联网后立即校正回 `quota` |
| 代跑 / 服务器代挂 | 上传 token 让服务端代签到 / 代做任务 | 改回「本机」模式**不会**停止代跑，服务端记录仍在跑 |
| 未开放 | 活动没开始 / 入口未开的第三态 | 既不算领到也不算失败，晚窗仍可补 |
| 成长任务 | WorkBuddy 成长中心每日任务（含聊天类） | 幂等，仅 WorkBuddy 有 |
| 错峰间隔 | 多号之间的随机签到间隔 | 只加在号与号之间，首个号直接跑 |
| 凭证保鲜 | 本机定期把刷新后的 token 回传服务端 | 服务端不自己续期 |
| 仅服务器账号 | 别的设备上传的代跑记录 | 本机无凭证：不能改模式 / 查积分，只能删除（真删服务端记录） |
